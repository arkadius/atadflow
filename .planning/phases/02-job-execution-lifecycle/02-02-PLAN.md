    The current `submitJob()` method calls `sparkSubmissionService.submit(job, code)` synchronously, which is still correct -- Plan 01 kept submit() as a synchronous method that launches the process and returns (async monitoring happens via onExit callback). However, review and adjust the method:

    1. **submitJob()**: The flow is now: create Job as PENDING -> persist -> call sparkSubmissionService.submit(job, code) which sets RUNNING and launches process -> persist again -> return DTO. This is exactly the existing pattern. The key change: submit() may now throw RuntimeException if the process fails to start (IOException wrapped). Wrap the submit call in try-catch:
       - On success: job will be RUNNING (set by SparkSubmissionService). Persist and return.
       - On failure: job will already be FAILED (set by SparkSubmissionService in its catch block). Persist and return -- do NOT re-throw. The caller (REST endpoint) should still get a 201 with the job in FAILED status, not a 500 error. This way the user can see the failure in the UI.

       Updated submitJob():
       ```java
       @Transactional
       public JobDto submitJob(SubmitJobRequest request) {
           Flow flow = Flow.findById(request.flowId());
           if (flow == null) throw new FlowNotFoundException(request.flowId());

           FlowDto flowDto = flowMapper.toDto(flow);
           String code = codeGenerationService.generateCode(flowDto);

           Job job = new Job();
           job.flow = flow;
           job.status = JobStatus.PENDING;
           job.submittedAt = LocalDateTime.now();
           job.persist();

           try {
               sparkSubmissionService.submit(job, code);
           } catch (Exception e) {
               // submit() already set job to FAILED with error message
               LOG.warnf("Job %s failed to start: %s", job.id, e.getMessage());
           }
           job.persist();

           return mapper.toDto(job);
       }
       ```

       Add a Logger field: `private static final Logger LOG = Logger.getLogger(JobService.class);`
       Add import: `import org.jboss.logging.Logger;`

    2. **cancelJob()**: No changes needed. It already delegates to sparkSubmissionService.cancel(job) and sets finishedAt. The cancel method in SparkSubmissionService now handles the real process killing.

    3. **listJobs() and getJob()**: No changes needed.

    The existing tests assert `status = "SUBMITTED"` which was the stub behavior. With the real SparkSubmissionService:
    - In the test environment, `python.executable` defaults to `venv/bin/python3` which likely does NOT exist in the Testcontainers-based test environment.
    - Therefore, `submit()` will throw an IOException, and the job will land in FAILED status.
    - Alternatively, configure a test-specific python.executable that does exist, but this would actually launch a real Python process during tests -- not desirable for unit/integration tests.

    **Strategy: Override python.executable in test profile to a non-existent path and assert FAILED status.** This is the pragmatic approach -- it tests the full error handling path. Testing the RUNNING/SUCCEEDED path requires a real Python+PySpark environment which is an integration/E2E concern.

    Alternatively, use a simpler approach: **don't override python.executable at all** -- the default `venv/bin/python3` will fail in test env, and jobs go to FAILED. Just update test assertions.

    Changes to `JobResourceTest.java`:

    1. **submitAndGetJob()**: Change status assertion from `"SUBMITTED"` to either `"RUNNING"` or `"FAILED"`. Since Python is not available in test env, expect `"FAILED"`. Update both assertions:
       ```java
       .body("status", anyOf(equalTo("RUNNING"), equalTo("FAILED")))
       ```
       Use `anyOf` matcher because: if tests run on a machine WITH Python+PySpark available (like the dev machine), the job may actually start. Using `anyOf` makes the test work in both environments.

       Also assert that the status is not "SUBMITTED" (that status no longer occurs in the flow).

       For the GET check afterward, use the same `anyOf` matcher.

    2. **cancelJob()**: The cancel test submits a job then cancels it. Since the job might be FAILED (Python not available) or RUNNING, cancel should still work -- SparkSubmissionService.cancel() handles both cases. The cancel assertion `status = "CANCELLED"` should remain correct since cancel always sets CANCELLED regardless of prior state. Keep this assertion as-is.

    3. **listJobs(), listJobsByFlowId(), getJobNotFound()**: No changes needed -- they don't assert on job status.
